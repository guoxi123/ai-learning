# Agent Teams vs Subagents：区别、优缺点与使用场景

> 面向刚接触 Claude Code 多智能体编排的读者。读完你能回答一个问题：
> **手头这个任务，该派一个 subagent，还是组一个 agent team？**

---

## TL;DR（太长不看）

- **Subagent（子智能体）**：在当前会话里临时召唤一个「外援」，干完一件独立的事，把结果交回来就结束。**单向汇报，彼此不交流。**
- **Agent Team（智能体团队）**：由一个 lead（你的主会话）牵头，拉起若干个有名字、能互相发消息、共享一个任务看板的队友，长期协作。**成员之间可以直接对话、自己认领任务。**

一句话决策：

> **要不要让干活的几个 agent 互相沟通？**
> 不需要 → 用 subagent；需要 → 用 agent team。

---

## 两个生活化比喻

把这两种模式想象成两种用人方式，区别一下就清晰了。

### Subagent ＝ 外包自由职业者

你是个项目经理（主会话）。你把一件边界清晰的事——比如「帮我查一下这个函数被哪些地方调用」——交给一个自由职业者（subagent）。

- 他带自己的工位（独立的上下文窗口），不看你之前的聊天记录。
- 他干完，把**成果摘要**交给你，结账走人。
- 你可以同时外包给好几个人，但他们**互相不认识、不交流**，只对你负责。
- 谁做什么、结果怎么合并，全靠你（主会话）来调度。

### Agent Team ＝ 项目作战室（war room）

你组建了一个固定项目组：一个前端、一个后端、一个测试。他们坐在同一个作战室里。

- 每个人有名字（teammate），你能直接 `@` 任何一个人单独交代。
- 他们**共享一块任务看板**（task list），干完一件事自己认领下一件。
- 前端和后端能**直接对话**商量接口，不用事事通过你传话。
- 你（lead）负责分工、综合结果，但日常协调他们自己搞定。

记住这个对比，后面的技术细节都是在解释这两张图。

## Subagents 详解

### 是什么

Subagent 是在**当前会话内部**启动的一个子智能体。它有自己的上下文窗口、自己的工具集和系统提示，接到一个任务后独立执行，完成后把结果摘要返回给主会话。

你可以用内置的 agent 类型（如 `general-purpose`、`Explore`、`Plan`），也可以在 `.claude/agents/` 下用 Markdown 文件自定义专门的 agent。

一个自定义 subagent 的定义长这样（`.claude/agents/code-reviewer.md`）：

```markdown
---
name: code-reviewer
description: Reviews code diffs for bugs and simplification opportunities. Use when the user asks to review changes.
tools: Read, Grep, Glob, Bash
model: sonnet
---

你是一个严格的代码审查员。只关注正确性和可简化点，
发现问题按严重程度排序输出。
```

定义一次，既能当 subagent 被主会话调用，也能在 agent team 里当 teammate 角色复用。

### 优点

- **上下文隔离**：子任务在独立窗口里跑，结果以摘要形式回传，**不污染主会话上下文**。主会话只看到一个结论，不用吞下中间过程。
- **省钱**：token 开销低，因为只有「结果」回流到主上下文。
- **可并行**：在一条消息里发多个 Agent 调用，多个 subagent 同时干活。
- **专业化**：每个 subagent 可以限定工具和提示，做成「只懂搜索」「只懂审查」的专家。
- **生命周期简单**：召唤 → 执行 → 返回，没有长期协调负担。

### 缺点

- **单向、一次性**：返回结果基本就结束了，多个 subagent 之间默认不通信，难以持续协作。
- **协调靠主会话**：如果任务之间有依赖或需要互相质疑，主会话得反复充当「传话筒」和「仲裁者」，啰嗦且容易丢信息。
- **共享信息重复加载**：每个 subagent 是独立上下文，公共背景信息可能被反复读入。

### 适合的场景

- **代码探索 / 搜索**：「找出所有处理支付的入口」「这个配置项在哪用」——只要结论不要过程。
- **独立的单点任务**：生成一个函数、写一个测试文件、跑一次类型检查。
- **并行无依赖任务**：同时对 3 个模块各做一件事，互不影响。
- **给主会话减负**：把会撑爆上下文的大块工作切出去，只收回摘要。

## Agent Teams 详解

### 是什么

Agent team 是**多个 Claude Code 实例协作**的机制。你的主会话作为 **team lead**，根据你的自然语言描述拉起若干 **teammate**，每个 teammate 是一个独立的 Claude Code 会话实例。

关键机制：

- **共享任务列表（task list）**：任务有 `pending / in progress / completed` 三种状态，还能设置依赖。teammate 干完一件可以自己认领下一件（用文件锁防止抢占）。
- **成员间直接通信（mailbox / SendMessage）**：任何 teammate 都能按名字给另一个发消息，消息自动送达，lead 不用轮询。
- **可直接对话**：你可以绕过 lead，直接点开某个 teammate 单独交代、追问或改方向。
- **可复用 subagent 定义**：spawn teammate 时可以引用 `.claude/agents/` 里的 subagent 类型，让 teammate 继承其工具白名单和模型。

> ⚠️ Agent teams 目前仍是**实验特性**，默认关闭。需要设置环境变量开启：
> ```bash
> export CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1
> ```
> （也可写进 `settings.json`）

### 优点

- **真正的协作**：成员能分享发现、互相质疑、自行分工，适合需要「讨论」才能推进的复杂工作。
- **抗锚定 bias**：调试时让多个 teammate 各持一种假设并**主动反驳对方**，比单线调查更不容易卡在第一个看似合理的解释上。
- **并行 + 协调**：既能并行探索，又能在交叉点上对齐（比如前后端各自实现后碰接口）。
- **持续可寻址**：teammate 有名字、长期在线，你可以随时插入指挥。

### 缺点

- **贵**：每个 teammate 都是独立的 Claude 实例，token 随 teammate 数量**大致线性增长**。社区实测复杂任务下整体开销可达单会话的数倍（有报道约 7 倍，非官方数字，仅供参考）。
- **协调开销大**：通信、任务状态同步、避免文件冲突都需要成本；teammate 多到一定程度收益递减。
- **更难调试**：多 agent 交互、消息时序、任务状态滞后（teammate 有时忘记标记任务完成，会卡住依赖任务）都是真实存在的坑。
- **当前限制不少**（实验阶段）：一个会话只能有一个 team、不能嵌套 team、in-process teammate 不支持 `/resume`、teammate 不能跑后台 subagent 等。
- **杀鸡用牛刀**：顺序任务、同文件改动、强依赖的工作用 team 反而更慢更贵。

### 适合的场景

官方点名的强场景：

- **研究与审查**：多个 teammate 同时从不同角度调查一个问题，互相分享并挑战对方的结论（如安全 / 性能 / 测试覆盖率三路并行 code review）。
- **新模块 / 新功能**：每个 teammate 各自拥有一块，互不踩脚。
- **竞争性假设的调试**：并行验证多种根因猜想，收敛更快。
- **跨层协调**：一次改动横跨前端、后端、测试，各由一个 teammate 负责。

> 官方建议：新手**先从研究和审查类任务入手**（边界清晰、不写代码），体会并行探索的价值，再过渡到并行实现。

## 核心对比表

| 维度 | Subagents | Agent Teams |
| --- | --- | --- |
| **架构** | 层级：父 → 子 | 扁平：lead + 对等 teammates |
| **上下文** | 独立窗口，结果回流给调用者 | 独立窗口，完全独立（不继承 lead 对话历史） |
| **通信** | 只向主会话回报结果 | 成员之间直接发消息 |
| **协调** | 主会话管理一切 | 共享任务列表，成员自协调、自认领 |
| **token 成本** | 低（结果摘要回流） | 高（每个 teammate 独立实例，随数量线性增长） |
| **成熟度** | 稳定，默认可用 | 实验特性，需手动开启 |
| **最适合** | 只关心结果、聚焦独立的任务 | 需要讨论、互相质疑、协作的复杂工作 |

## 怎么选：60 秒决策指南

按下面顺序自问：

1. **这件事需要多个 agent 互相沟通吗？**
   - 不需要 → **Subagent**（绝大多数情况）。
   - 需要 → 继续。
2. **任务能拆成彼此独立、互不踩脚的子任务吗？**
   - 不能（顺序依赖、改同一个文件）→ 用**单会话**或 **subagent**，别上 team。
   - 能 → 继续。
3. **复杂度和 token 预算值得吗？**
   - 值得（研究、审查、跨层大功能）→ **Agent Team**。
   - 不值得（常规小任务）→ **Subagent 或单会话**更划算。

速查：

| 你的任务长这样 | 推荐 |
| --- | --- |
| 查代码、读文档、找个符号 | Subagent |
| 写一个独立函数 / 一个测试文件 | Subagent |
| 同时审查多个维度（安全+性能+测试） | Agent Team |
| 一个 bug，有几种猜测想并行验证 | Agent Team |
| 一个大功能要拆前端/后端/测试并行做 | Agent Team |
| 顺序步骤、改同一批文件 | 单会话 / Subagent |

## 常见误区

- **「Subagent 会继承主会话全部上下文」**——不准确。Subagent 有**自己独立的上下文窗口**，只收到主会话写给它的任务提示，看不到主会话的聊天历史。它和 teammate 一样是隔离的；差别在**通信方式**，不在上下文继承。
- **「Team 一定更快」**——不一定。协调、消息往返、避免文件冲突都要时间。强依赖或同文件的任务，team 往往比单会话更慢。
- **「人多力量大」**——官方建议从 **3–5 个 teammate** 起步，每个 teammate 分到 5–6 个任务比较舒服。再多就协调开销超过收益，三个专注的 teammate 常胜过五个散漫的。
- **「Team 能取代 subagent」**——两者互补。Team 里每个 teammate 的「角色」其实就是复用一个 subagent 定义；subagent 是更轻量的基础积木。

## 延伸：和其他并行方式的位次

Claude Code 里「并行 / 委托」其实有几个层次，别混了：

- **Subagent**：会话内的轻量委托，单向汇报。
- **Agent Team**：多实例协作，双向通信 + 共享任务。
- **Workflow（工作流脚本）**：用确定性脚本（`pipeline` / `parallel`）编排一批 subagent，适合「步骤固定、要可复现」的流水线，靠代码而非自然语言控制流程。
- **Git worktree + 多个手动会话**：自己开多个 Claude Code 会话各占一个工作树，没有自动协调，全靠你手动管理——最自由也最费心。

复杂度与自由度从低到高大致是：**Subagent < Workflow < Agent Team < 手动多会话**。
